r1.1 개정 요약 — 실측이 설계를 고친 지점

r1.0은 적재 전에 쓴 설계다. Phase 0~3을 실제로 돌리는 동안 설계가 틀린 곳이 네 군데 드러났고, 이 판은 그것을 반영한 것이다. 고친 결과보다 고친 근거가 오래 쓰이므로 근거를 함께 남긴다.

  • 잔량 판정 기준을 문서에서 원장으로 바꿨다(§3.2·§5). 3경로 출하가 겹치면 문서 합계가 주문수량을 넘는다 — hisense 품목 85가 문서 21 / 원장 20이었다. tx:shippedQty를 신설하고 잔량·납기 이행은 이 값으로만 판정한다. 취소분(status=9)을 빼지 않으면 초과출고가 있다는 틀린 결론에 이른다.
  • 클래스 14 → 16, 관계 16 → 20(§3.2·§3.3). 출하 라인(tx:ShipmentLine)이 없으면 3경로를 같은 단위로 셀 수 없었고, r1.0 클래스 표에는 그림에 그려 둔 tx:Document가 빠져 있었다. 관계는 customer·forOrder· shipsTo·shipsLot이 늘었다.
  • 거래처 병합 키를 사업자번호에서 사업자번호 + 이름으로 바꿨다(§4.2). 한 사업자번호 아래 서로 다른 납품처가 들어 있다 — 당진시청 한 번호에 103행 (여성가족과·민원위생과…), 휴게소 운영사 한 번호에 29행이 각각 다른 지점이다. 번호로만 접으면 수주의 기관명이 엉뚱한 이름의 객체에 붙어 납기 연락 대상을 잘못 가리킨다.
  • 적재 전 riot --validate를 없앴다(§9.3). 그래프 PUT이 파싱과 저장을 한 트랜잭션에서 처리하므로 검증이 중복이고, 컨테이너 안에서 JVM을 또 띄우는 것이 moai-fuseki 메모리 한도를 건드렸다. 적재가 5분+에서 3초로 줄었다.

트리플 규모도 추정(35만~52만)에서 실측 286,057로 교체했다 — 거래처 중복 정리가 r1.0의 예상대로 작동한 결과다(§9.2). 로드맵(§10)과 성공 판정(§11.2)에는 Phase 0~3의 실제 결과를, 미결 사항(§12)에는 해소된 항목과 새로 생긴 판단 두 건을 반영했다.

§ 01

지금 왜 — 3사 실측 진단

온톨로지를 "안 해도 되지만 있으면 좋은 것"으로 보면 이 문서는 필요 없다. 이 설계가 필요한 근거는 이미 발생한 장애와 재작업이다. Palantir가 온톨로지 안티패턴으로 열거한 네 가지 — System Silos, Department Silos, God Object, Kitchen Sink — 가 세 MES에 각각 실물로 존재하며, 그중 하나는 2026-08-07에 실제 회귀 장애를 냈다.

1.1이미 온톨로지가 도는 선례

맨땅이 아니다. 케어앤(caren)에서 이미 Apache Jena Fuseki를 도입해 운영 중이다 — moai-fuseki 컨테이너(7주 연속 가동) 안에 /moai와 /caren 두 데이터셋이 공존하고, care-domain.ttl 271 트리플로 질병→특기 추론(requiresSpecialty + broaderSpecialty 양방향 폐쇄)과 STT 어휘 개인화를 서비스하고 있다. SPARQL 클라이언트는 표준 라이브러리만 쓴 140행(ontology.py)이며, Fuseki가 죽어도 매칭·STT는 기존 경로로 조용히 폴백한다.

이 설계는 그 선례의 운영 방식을 그대로 물려받는다. 새 인프라를 세우는 제안이 아니라, 검증된 배치 위에 tx-mes 데이터셋 하나를 더하는 제안이다.

1.2적재 후 — 진단이 실제로 해소됐는지 (r1.1)

위 표는 r1.0의 진단이다. Phase 1~3을 적재한 뒤 같은 항목을 다시 확인했다. 해소됐다는 뜻은 온톨로지 쪽에서 해소됐다는 것이고, MES DB·화면은 그대로다(P2) — DB까지 합칠지는 여전히 판단 사항이다(§12 D2·D3).

공통 언어 부재 hisense에서 만든 자재 영향분석 질의가 graph 이름만 바꿔 infurs에서 그대로 돌았다 (자재 8종이 수주라인에 걸림). 점검 스크립트도 같은 구조를 세 사이트가 공유한다. infurs BOM이 9품목만 등록돼 있어 질의는 돌지만 답할 데이터가 적다(D8).
§ 02

설계 원칙 7개

이후 모든 설계 판단은 이 7개에서 파생된다. 원칙과 충돌하는 구현은 구현이 틀린 것으로 본다.

  • P1 시스템이 아니라 현실을 모델링한다 t_order_item을 OrderLine으로 옮기는 게 목적이 아니다. 현장 사람이 쓰는 말 — 수주, 품목, 작업지시, 로트, 포장, 출하 — 를 먼저 정의하고 테이블을 거기에 붙인다. 테이블이 없으면 객체를 만들지 않고, 테이블이 둘이어도 객체는 하나다.
  • P2 MES DB가 단일 진실원천(SSOT)이다 온톨로지는 읽기 투영(read model)이다. 트리플스토어에 원본만 있는 데이터는 만들지 않는다. 온톨로지를 지우고 다시 만들어도 업무는 멈추지 않아야 한다.
  • P3 IRI로 ID 공간을 물리적으로 분리한다 hisense가 치른 item_id 회귀는 두 ID 공간이 같은 이름을 썼기 때문에 생겼다. IRI는 클래스를 이름에 포함하므로 같은 실수가 구조적으로 불가능하다(§4.2).
  • P4 시계열은 온톨로지에 넣지 않는다 naturefood mes_gathering_sensor는 85,610행이고 계속 늘어난다. 온톨로지에는 SensorChannel 정의·임계값·설비 연결만 두고, 측정값은 SQL에 남긴다. 판단에 쓰는 것은 "가동/비가동" 같은 해석된 상태다.
  • P5 Action은 온톨로지가 실행하지 않는다 쓰기는 전부 기존 MES 엔드포인트(Command)를 거친다. 이미 검증된 불변식 — 3경로 이중차감 방지, 출고 상한, 포장 내역서=실제출고 — 을 우회하는 쓰기 경로를 새로 만들지 않는다(§6).
  • P6 자연어는 조건만 파싱하고, 실행은 화이트리스트가 한다 hisense 품목조회·naturefood 대시보드 NL검색에서 이미 채택한 원칙. LLM이 SPARQL/SQL을 생성해 그대로 실행하는 구조는 채택하지 않는다.
  • P7 폴백 경로를 제거하지 않는다 Fuseki 미기동·타임아웃 시 모든 화면은 온톨로지 없이 기존 SQL 경로로 동작해야 한다. 타임아웃 상한은 caren과 동일하게 1.5s에서 시작한다.

4.2IRI 규칙 — ID 이중공간을 구조적으로 없앤다

2026-08-07 hisense 장애의 원인은 item_id라는 이름이 두 가지를 가리켰다는 것이다. 16개 생성지점의 의미를 통일했더니 읽기측 12개 파일이 옛 의미를 그대로 읽어 회귀했다. IRI는 클래스와 사이트를 이름 안에 포함하므로, 두 ID가 우연히 같은 문자열이 되는 일이 구조적으로 불가능하다.

IRI 생성 규칙

http://mes.telomx.kr/id/{site}/{Class}/{naturalKey}

  • {site} — infurs | hisense | naturefood. 사이트를 IRI에 넣어 named graph와 이중 방어.
  • {Class} — §3.2 클래스명 그대로. 이 조각이 ID 공간을 분리한다.
  • {naturalKey} — PK가 아니라 업무 키를 우선한다. Order는 order_no, Item은 item_code, Lot은 lot_no. PK는 업무 키가 없을 때만 쓰고 그 경우 pk- 접두어를 붙인다(OrderLine/pk-23).
  • 업무 키를 쓰는 이유: 전체 재적재(full reload) 후에도 IRI가 안 바뀌어 외부에서 인용한 링크가 유지된다.

r1.1 — 적재하며 추가된 규칙

업무 키를 쓰려면 그 키가 정말 유일한지를 적재가 확인해야 한다. 아래 넷은 실제로 안 유일했던 사례에서 나왔다.

  • 자연키가 비었거나 중복이면 pk-로 떨어뜨리고 결함으로 기록한다. 조용히 넘어가면 서로 다른 두 행이 한 객체로 합쳐진다 — 발견하기 가장 어려운 종류의 사고다.
  • infurs WorkOrder는 처음부터 PK를 쓴다. wo_no가 수주 단위로 발급돼 라인마다 중복이다(WO-260727-004가 2행). 자연키로 쓰면 두 작업지시가 한 객체가 된다.
  • Partner의 자연키는 사업자번호 + 이름이다 — Partner/biz-3118301218-당진시청 형태. 번호만 쓰면 한 법인의 부서·지점이 뭉개지고(당진시청 103행), 이름만 쓰면 동명의 다른 사업체가 합쳐진다(개별화물이 서로 다른 14곳). 실측 92개 법인이 부서·지점을 갖고 있고, 그것들은 tx:bizNo가 같아 질의로 묶인다.
  • 모든 객체는 tx:sourceTable·tx:sourcePk를 싣고, 병합된 객체는 tx:mergedFrom을 원천 행마다 하나씩 싣는다. 병합은 판단이고, 되짚을 수 없는 판단은 쓸 수 없다. 점검이 mergedFrom 총합을 DB 행 수와 맞춰 병합 중 조용히 사라진 행을 잡는다(infurs 28,056 = 28,056).
§ 05

판단 규칙은 이미 전부 존재한다. 문제는 그것이 PHP 컨트롤러 안에 흩어져 있어서 같은 규칙이 사이트마다 다르게 구현되고, 어느 화면이 어느 규칙을 쓰는지 아무도 모른다는 것이다. Logic 계층의 목적은 규칙을 새로 만드는 게 아니라 등록하는 것이다 — 온톨로지에는 규칙의 식별자·입력 객체·임계값·구현 위치를 두고, 계산 자체는 기존 코드가 한다.

§ 06

Action — 실행은 MES가 한다

블로그가 강조한 "Action Loop를 닫는다"는 부분은 우리 환경에서 가장 조심해야 하는 대목이다. 팔란티어는 Foundry가 원천이라 온톨로지가 직접 write-back한다. 우리는 반대로 MES DB가 원천이고, 그 DB에는 이미 피로 배운 불변식이 걸려 있다.

이미 존재하는 불변식 — 우회하면 안 되는 것들

  • 3경로 이중차감 방지 — 판매출고가 sales_order/package/delivery 세 경로로 발생하며, 같은 수량이 두 번 차감되면 안 된다.
  • 출고 상한 — 배정 로트 분기가 상한을 적용하지 않아 초과출고가 났던 이력. 상한은 품목별 잔량 기준.
  • 포장 내역서 = 실제 출고 — 이 등식은 확정된 불변식이다.
  • 작업지시 생성은 공용 헬퍼만 — resolve_master_item_id() / link_work_order_to_plan(). 16지점 일원화 결과를 되돌리는 경로를 만들지 않는다.
  • 마이그레이션 실패 시 코드까지 롤백되는 배포 스크립트가 있다 — 스키마 변경은 최소화한다.

Action 정의 형식

온톨로지에 등록하는 Action은 "무엇을 할 수 있는가"의 선언이며, 실행 주체는 항상 MES다. 각 Action은 ① 대상 클래스 ② 호출할 엔드포인트 ③ 필요 권한 ④ 검증할 불변식 네 가지를 갖는다. 1차 등록 대상은 이미 화면이 있는 것들로 한정한다 — 작업지시 발행, 공정 진척 기록, 포장 묶음 생성, 출하 확정, 재고 이동, 배송완료 처리.

§ 07

Security — 사람과 AI를 같은 체계로

AI가 조회·실행을 하기 시작하면 권한은 부가기능이 아니라 구조가 된다. 다행히 우리에게는 이미 권한 테이블이 있다 — t_user/t_permission/t_menu(infurs·hisense), mes_menu_users 430행(naturefood). Action의 권한은 새로 정의하지 않고 이 메뉴 권한에 매핑한다.

  • Fuseki는 localhost 바인딩을 유지한다. moai-fuseki는 host network + --localhost로 떠 있다. 외부 노출 금지 — 웹에서 SPARQL 엔드포인트를 직접 부르는 구조를 만들지 않는다.
  • 질의는 서버측 화이트리스트만. 파라미터만 바인딩하는 고정 SPARQL 템플릿. 자연어는 조건 파싱에만 쓴다(P6).
  • 행 단위 제한은 named graph로. 사용자가 속한 사이트의 graph만 질의 대상에 포함한다. 사이트 간 조회는 Phase 4에서 별도 권한으로.

  • 선결 조치 r1.1 부분 해소. login.php에 admin 비밀번호가 평문으로 박혀 있던 문제는 hisense는 코드 제거·비밀번호 교체까지 완료됐다(2026-09-20 확인). infurs와 ssfc는 그대로 남아 있다(같은 원본에서 갈라진 세 사이트의 공통 결함). 9.3동기화 방식 (r1.1 — 실제 운영 값으로 교체)

  • 야간이 아니라 매시 전체 재적재. 실측 적재 시간이 hisense 3초 · naturefood 6초 · infurs 14초라 야간까지 기다릴 이유가 없었다. cron은 :25 / :40 / :55로 나눠 서로, 그리고 백업(OOM 이력)과 겹치지 않게 뒀다. 증분 ETL은 만들지 않았다 — 전체 재적재가 이 속도면 증분 로직의 버그 위험을 살 이유가 없다(2차 계획은 보류).
  • 그래프 단위 PUT이 트랜잭션이다. 적재는 PUT /data?graph=… 하나로 통째 교체된다. 실패하면 아무것도 바뀌지 않으므로 이전 그래프가 그대로 남는다(부분 적재 없음) — 실측 확인.
  • 적재 전 riot --validate는 없앴다. PUT이 파싱과 저장을 한 트랜잭션에서 하므로 깨진 입력은 400(줄·칸 번호 포함)으로 거부되고 그래프는 보존된다. 검증을 컨테이너 안에서 JVM으로 또 돌리던 것이 moai-fuseki 메모리 한도에 붙어 스래싱했다 — 다시 넣지 말 것(적재 5분+ → 3초).
  • 겹침 방지와 상태 노출. cron 진입점은 flock으로 겹침을 막고, 한 줄 로그와 out/status.json(data_at = 마지막으로 성공한 적재 시각)을 남긴다. 실패한 실행이 이 값을 밀어 올리면 화면이 방금 기준이라고 거짓말한다 — 그래프는 옛것 그대로인데. hisense /impact는 이 값을 데이터 기준 시각 칩으로 띄우고 2회분(2시간 30분)을 넘기면 경고한다.
  • 불변식 점검. 적재 직후 자동 실행되며 실패하면 종료코드 1이다. 항목 수는 hisense 25 · naturefood 25 · infurs 34. 세 사이트가 같은 구조를 공유하되 사이트 고유 불변식을 더한다 — infurs는 병합 근거 총합 = DB 행 수, 공통으로 한 IRI가 두 클래스를 가짐 = 0 · 스키마에 없는 술어 = 0 · 원장 실출고 = 그래프 출하수량.
  • 외부 의존 없음. 이 서버는 npm·jsdelivr·Docker Hub·Cloudflare 대역이 차단돼 있다. ETL은 서버에 이미 있는 PHP CLI 또는 표준 라이브러리 Python으로만 만든다(caren ontology.py가 urllib만 쓴 이유).

  • 온톨로지에만 있는 데이터를 만들지 않는다. 예외는 임계값(§5)뿐이며, 그것도 DB에 반영 경로를 함께 만든다.
  • 기존 화면을 Fuseki 의존으로 바꾸지 않는다. 온톨로지는 새 화면을 추가할 뿐이다.
  • LLM이 생성한 질의를 그대로 실행하지 않는다.
  • 새 Fuseki 인스턴스·새 컨테이너를 띄우지 않는다. RAM 제약(§9.1).
  • 적재 과정에서 JVM을 따로 띄우지 않는다. r1.1 추가 riot --validate를 컨테이너 안에서 돌리던 것이 메모리 한도에 붙어 스래싱했다(§9.3). 검증은 PUT이 트랜잭션으로 한다.
  • 병합한 객체에서 원천 행을 지우지 않는다. r1.1 추가 두 마스터를 한 객체로 합칠 때 tx:mergedFrom으로 원천 행을 전부 남긴다. 되짚을 수 없는 병합은 검증도 못 하고 틀렸을 때 고칠 수도 없다(§4.2).
