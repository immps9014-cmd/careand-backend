§ 01

왜 MCP인가

적재는 끝났지만 쓰는 곳이 적다. Fuseki tx-mes 데이터셋에 hisense·infurs·naturefood 세 그래프가 매시간(:25/:40/:55) 갱신되는데, 그래프를 읽는 화면은 hisense 영향분석 하나뿐이다. infurs 180,337 트리플과 naturefood 87,672 트리플은 쌓이기만 하고 읽히지 않는다.

지금의 막힘MCP가 바꾸는 것
새 질문마다 화면을 개발해야 함검증된 질의를 도구로 한 번만 노출하면 Claude가 질문에 맞게 골라 호출
Onto-Ask 향후 계획 1번 — 자연어를 그래프 질의에 직접 연결하지 못함Claude가 질문 해석기 역할을 맡고, 서버는 화이트리스트만 실행
LLM 크레딧 부족(D6) — hisense 자연어 검색·OCR Vision 경로가 실운영에서 검증되지 못함LLM 비용이 사용자 쪽 Claude 구독으로 넘어감. MES 서버에 API 키가 필요 없음
3사 데이터를 한 번에 볼 수단이 없음site 파라미터 하나로 같은 도구가 세 그래프에 동작(재사용 판정 §11.2에서 이미 실측)
MES 데이터와 메일·일정·PMS가 따로 놂Gmail·Calendar·PMS 등 다른 MCP와 한 대화 안에서 조합

쓰기(Action)는 이 경로를 타지 않는다. 쓰기 도구를 붙이게 되면 기존 MES 엔드포인트를 호출한다(§04).

설계 원칙과의 대응

MCP는 새 원칙을 만들지 않는다. 설계서가 이미 정한 세 원칙이 그대로 MCP의 구성 요소가 된다. 검증된 질의만 실행은 도구 목록이 되고, MES DB가 원본, 그래프는 읽기 투영은 읽기 전용 서버가 되며, 쓰기는 MES 엔드포인트로만은 확인 절차가 붙은 별도 도구가 된다.

§ 02

도구 카탈로그

§ 03

효과가 큰 활용 6가지

납기 위험 대응즉시 가능hisense
impact · Gmail

자재 지연 한 건에서 연락 초안까지 한 대화로 끝낸다. 영향받는 수주를 찾고, 연락 대상은 발주기관(조달청)이 아니라 수요기관으로 잡는다. 이 구분은 Phase 3에서 온톨로지에 이미 들어가 있다.

“알루미늄 프레임 입고가 1주 밀리면 영향 수주랑 수요기관 정리하고 연락 메일 초안 써줘”
자연어 질의즉시 가능3사 공통
Onto-Ask 연결

Onto-Ask의 해석 단계를 Claude가 맡는다. 규칙 파서가 못 잡던 질문도 도구 선택으로 처리되고, 답에는 어떤 도구를 어떤 조건으로 불렀는지가 남는다. 기술개요서의 “자연어 질문 처리율” KPI를 도구 호출 로그로 잴 수 있다.

“이 수주 몇 개 남았어?” → order_remaining(site=hisense, order_no=…)
데이터 정합성 점검즉시 가능3사
check · verify

§ 04

지켜야 할 선

  1. G1
    SPARQL 원문 도구는 기본으로 두지 않는다AI가 질의를 직접 만들지 않는다는 Onto-Ask 원칙을 스스로 깨게 된다. 필요하면 관리자 전용으로만 두고 읽기 전용, LIMIT, 타임아웃을 강제한다.
  2. G2
    Fuseki 메모리 한도를 지킨다moai-fuseki 컨테이너는 1GB 제한이다. 도구마다 타임아웃(현재 라이브러리 1.5초)과 결과 행 상한을 둔다. 컨테이너 안에서 JVM을 따로 띄우는 검증은 금지(과거 스래싱 사례).
  3. G3
    모든 응답에 데이터 기준 시각을 넣는다/impact의 “데이터 기준 hh:mm” 칩과 같은 이유다. 2시간 30분을 넘기면 응답에 경고를 붙인다.
  4. G4
    모호하면 고르지 않는다이름 해소 후보가 여럿이면 목록을 돌려주고 사용자 선택을 기다린다. 동명이인 거래처에 잘못 붙은 답은 납기 연락 대상을 틀리게 만든다.
  5. G5
    쓰기는 MES 엔드포인트로만, 사람 확인 후에만불변식을 우회하는 쓰기 경로를 만들지 않는다. 작업지시 생성은 Order::pipeline_action 재사용 원칙 그대로.
  6. G6
    외부 공개 전에 인증과 선결 과제를 끝낸다원격 MCP는 OAuth 또는 토큰 인증 필수. infurs 평문 비밀번호(D7) 해결이 먼저다. 개인정보는 그래프에 싣지 않는다는 원칙(caren)도 유지한다.
§ 05

단계별 도입

순서가 중요하다. 외부 공개가 없는 단계부터 시작하면 보안 선결 조건 없이 효과를 먼저 확인할 수 있다.

단계내용사용처선결 조건
M1 ✔stdio MCP 서버 · 읽기 전용 도구 5~6개(impact · remaining · invariants · doc_vs_ledger · resolve_entity) + 리소스 4종lt-server의 Claude Code없음
M2 ✔도구 호출 로그 적재 → “자연어 질문 처리율” KPI 산출. trace_lot · partner_360 · data_gaps 질의 추가동일신규 질의는 check로 검산 후 화이트리스트 등록
M3 ✔HTTPS 원격 MCP 추가(Streamable HTTP, stdio 병행). 사이트별 권한은 보류 — 토큰 하나가 3사를 모두 본다claude.ai · Desktop · 다른 서버의 Claude Code토큰 인증 ✔ · D7 해결 ✔
M4확인 절차가 붙은 쓰기 도구(예: 배송지시 발행 요청) — MES 엔드포인트 호출현장 관리자도구별 불변식 확인 · 사용자 결정
서버 환경 제약

lt-server는 아웃바운드가 화이트리스트로 막혀 있다. MCP SDK는 npm 역터널(Verdaccio)로 Node SDK를 받거나, SDK 없이 stdio JSON-RPC를 직접 구현하는 두 길이 있다. 어느 쪽이든 질의 본문은 MCP 서버에 두지 않고 hisense Ontology::QUERIES를 호출한다. 3사 공용 화이트리스트를 한 곳에 두는 것은 mes-core.ttl을 hisense 레포에 두는 것과 같은 원칙이다.

자재 요약 질의가 출하 건수까지 수주로 셌다. tx:hasLine·tx:ofItem은 출하(Shipment─hasLine→ShipmentLine)도 쓰는 관계인데 클래스를 못 박지 않았기 때문이다. hisense ITM-0086에서 수주는 2건인데 8건(수주 2 + 출하 6)으로 나왔다. /impact 화면은 이 질의를 쓰지 않아 드러나지 않았고, MCP가 처음 이 값을 사람에게 보여 주는 소비자가 되면서 나왔다. tx:Order·tx:OrderLine으로 못 박아 고쳤고, 자체 시험에 “ITM-0086 = 라인 5 · 수주 2”를 넣었다.

  • freshness를 응답 맨 앞에 둔다. data_at · age_min · stale(150분 초과). stale이면 “최신이라고 말하지 말라”는 문장이 함께 간다.
  • 이름 해소는 정확히 같은 이름을 앞으로 올리되, 정확히 같은 후보가 여럿이어도 고르지 않는다. infurs “충청남도 교육청”은 사업자번호가 있는 객체와 없는 객체 2개가 정확히 일치한다.

§ 08

도구를 5종 더해 10종이 됐다. 새 질의 11개는 모두 Ontology::QUERIES에 넣었고, 도구로 열기 전에 3사 MES DB 직접 집계와 대조했다. 대조 스크립트는 도구가 부르는 바로 그 질의로 그래프를 읽고, DB 쪽은 적재기를 거치지 않고 원천 테이블에서 센다. 비슷한 SPARQL을 검산용으로 따로 쓰면 도구를 검증하지 못하기 때문이다.

개인 연락처는 대화로 내보내지 않는다

infurs 거래처 객체에는 담당자 이름·전화·이메일·대표자명이 적재돼 있다. MCP 응답은 대화에 그대로 실리므로 partner_meta 질의가 이 속성을 아예 고르지 않는다. 대조 스크립트가 3사 각 40개 거래처로 누출이 없는지 매일 확인한다. 거래처 360에 필요한 것은 법인·지점 구분과 이력이다.

자연어 질문 처리율 KPI

MCP 서버에는 질문이 아니라 도구 호출이 들어온다. 그래서 답하는 도구마다 선택 인자 question(질문 원문)을 두고, 호출마다 결과 분류와 함께 out/mcp-calls.jsonl에 남긴다.

항목정의
질문한 세션 안에서 같은 question 문장으로 들어온 호출 묶음
처리그 묶음에 답(answered)이나 “해당 없음” 답(empty)이 하나라도 있음. 후보만 주고(ambiguous) 사용자가 고른 뒤 다시 불러 답하면 처리다
미처리 사유도구 없음(log_unanswered) > 그 사이트엔 없는 데이터(unsupported) > 후보만 주고 끝남 > 오류
한계도구를 한 번도 안 부르고 끝난 질문은 log_unanswered로만 잡힌다 — 질문 수는 하한이다. question 없는 호출은 따로 센다

자체 시험이 질문 5개(처리 2 · 도구 없음 1 · 미지원 1 · 오류 1)를 흘려 처리율 0.4가 나오는지 확인한다. 시험 호출은 임시 로그로 가서 실제 KPI를 오염시키지 않는다. 로그에는 거래처 이름 같은 질문 원문이 들어가므로 소유자만 읽을 수 있게(0600) 만들고, git과 웹에서 제외된 out/에 둔다.

운영

  • 검산 cron — crosscheck.cron.sh 매일 06:58. 3사 재적재(:25 · :40 · :55)가 끝난 직후라 그래프와 DB의 시차가 가장 작다. 결과는 out/crosscheck.json과 status://{site} 리소스에 실린다. 소요 4초.

  • 원칙 추가 — 새 질의는 QUERIES에 넣고 crosscheck.php에 DB 대조를 더해 통과한 뒤에만 도구로 연다.

infurs와 ssfc(sslnc)의 로그인 화면은 저장된 계정이 없으면 관리자 아이디·비밀번호를 평문으로 채워 넣고 있었다. 로그인 페이지 소스만 열면 누구나 총괄관리자로 들어올 수 있었다. hisense에서 먼저 고친 방식(68adee7)을 그대로 따랐다.

경로 토큰이 로그에 남지 않게

경로 방식은 토큰이 URL에 들어가므로 접근 로그에 그대로 쌓일 수 있다. 두 곳을 막았다. PHP 내장 서버는 -q로 요청 로그를 끄고, Apache는 /mcp 요청을 "POST /mcp[path-hidden]" 형식으로만 남긴다. 실측으로 access_log와 journal에서 토큰 원문 0건을 확인했다. 이 두 설정 중 하나를 빼면 토큰이 로그에 남는다.

검증

  • 자체 시험 59항목(M2 46 → 59). HTTP 서버를 임시 포트와 임시 토큰 파일로 띄워 13항목을 더 본다. 무인증·폐기 토큰 401, 헤더·경로 토큰, 알림 202, stdio와 같은 답, 로그의 세션 id·토큰 이름, GET 405, 외부 Origin 403, 배치, /mcp 밖 경로 404, 분당 상한 429, 서버 로그에 토큰 원문 없음.
  • 운영 주소 — 무인증 401, 토큰으로 initialize·run_invariants·doc_vs_ledger 200. 권한을 좁힌 서비스 안에서도 점검 스크립트가 돈다. 같은 vhost의 /pms와 홈페이지는 200 그대로다.
  • 아직 안 한 것 — claude.ai·Desktop에서 실제 커넥터로 붙여 보는 시험. 이 서버는 헤어핀 NAT 때문에 자기 공개 도메인에 못 붙으므로 외부 클라이언트에서 확인해야 한다.

설계에서 달라진 점

  • OAuth 대신 사내 토큰. 공개 범위가 텔롬엑스 내부라 토큰으로 충분하다고 판단했다. 고객사 담당자에게 열려면(M-3 다) 그때 OAuth나 사이트별 토큰을 붙인다.
  • 사이트별 권한은 보류. 토큰 하나가 3사를 모두 본다. 반쯤 만든 권한 분리가 오히려 위험해서 넣지 않았다. 고객사에 열 때 같이 설계한다.
  • 새 서브도메인 대신 경로. *.aiclaude.kr는 DNS 와일드카드가 아니라 새 이름마다 레코드가 필요하고, 인증서 갱신도 막혀 있다(certbot 차단). 이미 인증서와 PMS 프록시가 붙은 telomx.aiclaude.kr 아래에 두었다.
  • root가 아닌 apache 권한. 앱 DB 설정과 점검 스크립트가 모두 apache로 읽히는 것을 확인했다. 외부에 열린 프로세스를 root로 돌리지 않는다.
