수주·작업지시 화면 정리안

수주를 등록하는 입구가 네 곳, 작업지시를 내는 입구가 일곱 곳입니다. 같은 일을 하는 버튼이 세 가지 이름으로 흩어져 있고, 수주 상세에서는 계획을 먼저 등록해야 작업지시 버튼이 열립니다. 현재 코드와 운영 DB를 직접 확인해 얽힌 지점을 정리하고, 입구 하나·편집기 하나·발행 버튼 하나로 모으는 안을 제시합니다. r1.1(2026-09-24): 결정 Q1~Q4가 모두 기본안으로 확정됐고 1~3단계를 구현했습니다. 2~4절은 구현 전 실측 기록이고, 결과는 9절에 있습니다.

1요약

문제 1입구가 흩어져 있다

수주 등록 4곳(보이는 것) + 숨은 2곳, 편집기 2벌, 저장 경로 2벌. 등록 방식마다 도착하는 화면이 다르다.

문제 2작업지시를 바로 못 낸다

수주 상세에서 작업지시 버튼은 계획등록 전까지 잠겨 있다. 서버는 계획을 자동으로 만드는데 화면만 막고 있다.

문제 3같은 일, 다른 이름·다른 코드

"생산요청"·"작업등록"·"작업지시 발행"이 같은 결과를 서로 다른 세 경로로 만든다.

제안의 뼈대 — ① 수주 등록은 수주 목록의 버튼 하나(방식 3가지 선택) ② 수주 편집기는 한 벌 ③ 작업지시는 수주 상세의 [작업지시 발행] 한 번(계획은 자동) ④ 세부 지시는 탭 편집기 하나 ⑤ 총무는 발행까지, 생산은 수락·진척·입고. 작업지시 생성 로직은 이미 Order::pipeline_action()으로 일원화돼 있어서, 대부분은 화면과 버튼을 정리하는 일입니다.

2수주 등록 현황

구현 전(r1.0) 실측입니다. "총무 > 수주" 목록 상단 버튼 3개와 "총무 > 작업지시" 화면의 버튼 1개가 보이는 입구입니다. 방식에 따라 서로 다른 편집기에 도착합니다.

3작업지시 발행 현황

구현 전(r1.0) 실측입니다. 작업지시를 새로 만드는 버튼이 네 화면, 일곱 곳에 있습니다. 코드 경로는 네 갈래입니다.

#내용영향상태
D1수주 수정 저장이 특이사항·FAX·담당자 연락처를 지운다. Order::update_order()가 memo·customer_fax·customer_contact_phone을 POST 값으로 덮어쓰는데, 수정 화면(order/form)에는 이 입력칸이 없다. 그래서 항상 빈 값이 저장된다.일반수주서(OCR)로 등록한 뒤 한 번이라도 수정하면 특이사항이 사라진다. 운영 수주 2건은 원래 비어 있어 아직 피해는 없다.수정 · 2001a7b
D2수주 상세에서 작업지시 단계가 계획 전까지 잠김(3절 A·B).클릭이 두 번 필요하고, 총무 > 작업지시 화면과 동작이 다르다.수정 · 2001a7b
D3발행 코드가 두 벌: 원클릭(pipeline_action)은 빈 "대기" 작업지시를 만들고, 생산요청 폼(WorkOrder::store)은 작업자·도면·지시사항을 받는다.같은 수주라도 어느 버튼으로 냈는지에 따라 작업지시의 내용이 다르다. 채번도 다르다(2026-08-15에 통일하지 않기로 결정).해소 · 4f2e65e
D4발행할 것이 없어도 "발행되었습니다". pipeline_action('work')가 이미 발행된 품목만 받아 아무것도 만들지 않아도 성공 문구를 띄웠다. (구현 중 발견)담당자가 발행됐다고 믿고 넘어갈 수 있었다.수정 · 4f2e65e
D5업로드 팝업은 납품기한 없이 저장됐다. order/form은 필수인데 pdf_save만 비워도 통과했다. (구현 중 발견)등록 뒤 수정하려 하면 그때서야 막혔고, 생산계획 기간을 잡을 수 없었다.수정 · 4f2e65e
D6수주 목록에서 클릭할 때마다 JS 오류, 생산입고 화면 로딩 때 배지 JS 오류. (브라우저 점검 중 발견)다른 동작은 막지 않았지만 콘솔 오류가 계속 쌓였다.수정 · 4f2e65e

원칙

  1. 입구 하나.수주 목록의 [수주 등록 ▾] 하나에서 방식 세 가지를 고른다. 총무 > 작업지시의 "＋ 수주 등록"은 없앤다. 그 화면은 발행 대기 목록으로만 쓴다.
  2. 편집기 한 벌.수주 편집 화면 하나에 필드를 모두 둔다(발주기관·품대계·수수료·특이사항·FAX·담당자 연락처). 업로드 팝업은 "인식 결과 확인" 단계로 남기되 같은 필드와 같은 저장 규칙을 쓴다.
  3. 발행 버튼 하나, 이름 하나."작업지시 발행". 누르면 계획이 없어도 자동으로 만들고 이어서 발행한다(서버는 이미 이렇게 동작한다). 수주 화면의 [계획등록] 단계 버튼은 없애고, 계획은 진행 표시로만 보인다. 기간·창고 조정은 생산계획 화면에서 한다.
  4. 세부 지시는 탭 편집기 하나.발행 직후 "작업자·도면·전달사항 입력" 링크로 workorder/edit/{수주}를 연다. 생산요청 폼(workorder/create)과 그 ✎는 이 편집기로 바꾼다.
  5. 역할 분리.생산 화면의 "수주 목록에서 생산요청"(E)은 총무 발행과 중복이라 없애고, 발행 대기 작업지시를 수락하는 기능만 둔다. 수주 없이 재고용으로 만드는 "직접 생산요청"(F)은 생산 고유 기능이라 유지한다.
  6. 생성 로직은 늘리지 않는다.새 버튼도 모두 Order::pipeline_action()을 부른다. 16곳에 흩어졌던 생성 지점을 모은 2026-08 리팩토링의 원칙을 화면까지 넓히는 것이다.
